Chapter 1

Overview & Background

Before tracing the boot sequence, understand the platform: what xv6 is, how RISC-V privilege modes work, and what QEMU provides.

🐧
What is xv6?

xv6 is a small, clean Unix-like operating system written at MIT for teaching. The RISC-V port runs on QEMU's virt machine and implements:

✓Multiple processes with virtual memory isolation
✓A simple on-disk file system (inode-based)
✓Pipes, fork, exec — full Unix process model
✓UART console, VirtIO disk driver
✓Sv39 virtual memory (3-level page tables)
✓Multi-hart (multi-CPU) support, up to 8 cores
⚡
RISC-V Privilege Levels

RISC-V defines three nested privilege levels. Each has its own CSRs and restrictions:

M — Machine Mode (Level 3)
Full hardware access. xv6 uses it only during early boot (_entry, start()) to configure CSRs, then exits permanently via mret.
S — Supervisor Mode (Level 1)
Kernel privilege. Controls page tables (satp), trap handlers (stvec). xv6 kernel runs entirely here after mret.
U — User Mode (Level 0)
Restricted access. Cannot touch CSRs or physical memory directly. System calls go through ecall → trampoline → kernel.
🖥️
What QEMU Provides
QEMU virt machine — the hardware platform xv6 runs on
🔄
ELF Loader
The -kernel flag causes QEMU to parse the kernel ELF binary and copy its PT_LOAD segments directly into simulated RAM at 0x80000000. No separate bootloader needed.
💻
8 RISC-V Harts
All 8 hardware threads (harts) simultaneously begin executing at 0x80000000 in Machine Mode with interrupts disabled. xv6 handles multi-hart coordination itself.
🔌
MMIO Devices
UART at 0x10000000, VirtIO disk at 0x10001000, PLIC at 0x0C000000, CLINT at 0x02000000. All accessed via memory-mapped I/O.
📐
Sv39 Virtual Memory
3-level page tables, 39-bit virtual address space

xv6 uses RISC-V's Sv39 paging scheme. A 39-bit virtual address is split into three 9-bit page table indices and a 12-bit page offset:

VA[38:30] VPN[2] → L2 page table index VA[29:21] VPN[1] → L1 page table index VA[20:12] VPN[0] → L0 page table index VA[11:0] offset → byte within 4KB page Max virtual address: 2^39 = 512 GB Page size: 4096 bytes (4 KB) PTE size: 8 bytes PTEs per page: 512

Key PTE permission bits used in xv6:

BitNameMeaning
PTE_VValidPTE is valid
PTE_RReadPage is readable
PTE_WWritePage is writable
PTE_XExecutePage is executable
PTE_UUserAccessible in U-mode
💡
TRAMPOLINE and TRAPFRAME are mapped without PTE_U, making them invisible to user code but accessible in S-mode during trap handling.

Boot Flow

Every stage the system passes through from QEMU power-on to a running shell — with the key registers set, privilege transitions made, and source functions called at each step.

🖥️
Stage 0 — QEMU Firmware
Physical address 0x1000 → jumps to 0x80000000
M-mode
1
QEMU emulates RISC-V virt machine — no separate BIOS chip, firmware is built into QEMU itself.
2
Firmware resets all harts to Machine mode at PC = 0x1000 — a small ROM stub.
3
The ROM stub loads the kernel ELF (via -kernel flag) into physical RAM at 0x80000000, then jumps there.
4
All CPUs (harts) start simultaneously; mhartid distinguishes them. Every hart enters _entry.
pc = 0x80000000
mhartid = hart ID
privilege = M
jumps to 0x80000000
⚙️
Stage 1 — _entry (entry.S)
Kernel entry point · sets up per-hart stacks
M-mode
1
stack0 is a 4096 × NCPU byte array in BSS. Each hart gets its own 4 KiB slice: sp = stack0 + (hartid+1)*4096.
2
The stack pointer is set by reading mhartid, multiplying by 4096, adding the base address of stack0, then adding 4096 to point to the top.
3
Jumps (via tail start) to the C function start() — still in M-mode, no stack frame yet.
4
Harts not yet ready spin on a lock in main() — only hart 0 proceeds first.
sp = stack0[(hartid+1)*4096]
privilege = M
tail start → start()
🔧
Stage 2 — start() (start.c)
Machine-mode CSR configuration · prepares mret to S-mode
M-mode
1
mstatus.MPP ← S — sets the "previous privilege" field so mret drops to Supervisor mode.
2
mepc ← main — tells mret to jump to main().
3
satp ← 0 — disables paging; physical addressing until kvminit() sets up page tables.
4
medeleg / mideleg ← 0xffff — delegates all exceptions and interrupts to S-mode handlers.
5
PMP — pmpaddr0 and pmpcfg0 grant S-mode read/write/execute to all physical memory.
6
timerinit() — enables SSTC extension, configures stimecmp for the first timer interrupt.
7
tp ← hartid — stores hart ID in the thread pointer register so cpuid() works in S-mode without a CSR read.
8
mret — atomically: restores MPP → S-mode, jumps to mepc (= main).
mstatus.MPP=S
mepc=main
satp=0
medeleg=0xffff
mideleg=0xffff
pmpaddr0
pmpcfg0=0xf
tp=hartid
mret → Supervisor mode
🧠
Stage 3 — main() (main.c)
Supervisor-mode kernel initialization · hart 0 bootstraps, others wait
S-mode
1
Hart 0 only: consoleinit() — UART device, enables console I/O.
2
kinit() — physical memory allocator: adds all free pages from end to PHYSTOP into the free list.
3
kvminit() — builds the kernel page table (device MMIO, kernel text, kernel data, per-process KSTACK regions).
4
kvminithart() — writes satp with the kernel page table PPN and flushes TLB with sfence.vma. Paging is now ON.
5
procinit(), trapinit(), trapinithart() — sets stvec to the trampoline's kernel trap vector.
6
plicinit() / plicinithart() — PLIC interrupt controller: enables UART and virtio device interrupts.
7
binit(), iinit(), fileinit() — block cache, inode cache, file table.
8
virtio_disk_init() — initializes the virtio block device (the disk).
9
userinit() — allocates PID 1, maps initcode binary at VA 0x0, sets up trapframe for first sret.
10
Other harts: spin until started==1, then run their own kvminithart()/trapinithart(), call scheduler().
satp = kernel pagetable
stvec = kernelvec
sie |= SEIE|STIE
scheduler() → first runnable proc
🌱
Stage 4 — userinit() / scheduler()
PID 1 created · first context switch · sret to user space
S-mode
1
userinit() allocates a struct proc, calls allocproc() which sets up the kernel stack and trapframe.
2
uvminit() allocates one page, copies the initcode binary (tiny exec syscall) into it at VA 0x0.
3
Trapframe is initialized: epc=0 (start of initcode), sp=PGSIZE (top of user page).
4
scheduler() finds PID 1 in RUNNABLE state, calls swtch() to swap to its kernel context.
5
usertrapret() prepares the return: sets stvec to trampoline uservec, loads trapframe into CSRs.
6
Trampoline's userret restores all user registers from trapframe, switches satp to the user page table, sret fires.
sepc = 0x0 (initcode)
satp = user pagetable
sstatus.SPP=0
sret → User mode
🐚
Stage 5 — initcode → /init → sh
User space · exec syscalls chain to the shell
U-mode
1
initcode runs at VA 0x0. It puts SYS_exec in a7, the string "/init" in a0, then ecall.
2
The ecall traps to S-mode via uservec (trampoline). The kernel handles it as a sys_exec call, loading /init from disk.
3
/init opens /dev/console as fd 0,1,2 then fork()+exec("/sh").
4
sh (the shell) starts, prints a prompt, and the system is now fully operational.
privilege = U
ecall → sys_exec
exec("/init") → exec("/sh")
Deep Dive

The Trampoline

The most critical design element in xv6. A single 4 KB page mapped at the same virtual address in every address space — essential for safe kernel/user transitions.

⚠️
The Core Problem: When a user-space trap fires, the CPU switches to S-mode but the user page table is still loaded in satp. The kernel's code is not mapped in user page tables — except for the trampoline page, which is mapped at TRAMPOLINE = MAXVA - PGSIZE in every page table.
User VA Space (any process)
Kernel VA Space
Why the Same Address in Both?

When a trap fires from user space:

1.
CPU sets PC = stvec = TRAMPOLINE + offset (uservec)
2.
CPU is now in S-mode, but satp still holds the user page table
3.
Code at TRAMPOLINE must be executable under the user page table (it is — mapped there without PTE_U)
4.
uservec switches satp to kernel page table
5.
After switch, PC still points into TRAMPOLINE — valid because it's mapped at the same VA in kernel space too
💡
Without this identity of VA, the csrw satp, t1 instruction would immediately invalidate the current PC, causing a fault.
